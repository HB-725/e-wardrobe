## 1. 产品是什么

一个手机上的电子衣橱。核心卖点是：**不管衣服怎么拍，进衣橱后都变成统一风格的商品图**（浅灰底、正面、居中、柔光，类似优衣库官网），然后可以把这些衣服**穿在用户自己的形象上**，像 QQ秀一样快速换装、转身查看，最后生成写实的上身大片。

### 优先级（用户确认）

1. 衣物管理（核心）
2. 穿搭制作与管理
3. AI 上身效果（个人形象、换装、旋转、真人大片）
4. 每日穿搭（天气、场合）——以后
5. 购物决策——以后

### 用户与规模

- 先给自己用（安卓），再给少量朋友试用（多数是 iPhone）。
- 不是商业产品，暂不上架应用商店。iOS 通过 TestFlight 分发，安卓直接发 APK。
- AI 费用由每个用户**用自己的 API Key** 承担（BYOK）。

### 非目标

- 不做尺码推荐或合身判断。上身图只用来看搭配效果。
- 不做真 3D 服装模型。"旋转"用 8 个预生成角度实现。
- 不做社交、分享广场、电商导购。

## 3. 技术架构

```
┌──────────────────────────────┐
│ 手机 App · Expo（React Native）│  安卓 + iOS 一套代码
│ · expo-router 路由            │
│ · 原生相机 / 相册              │
│ · 本机抠图原生模块              │  iOS Vision / Android ML Kit
│ · 换装：图层叠加渲染            │
│ · TanStack Query 数据缓存       │
└──────┬─────────────▲─────────┘
       │ 上传 / 建任务 │ Realtime 推送任务状态
┌──────▼─────────────┴─────────┐
│ Supabase                       │
│ · Auth（邮箱 / Apple / Google） │
│ · Postgres + 行级权限（RLS）     │
│ · Storage（私有桶，按用户分目录）│
│ · Queues（pgmq）任务队列         │
│ · Vault 加密保存用户 API Key     │
└──────┬─────────────▲─────────┘
       │ 领取任务     │ 写回结果 / 费用
┌──────▼─────────────┴─────────┐
│ AI 工作服务 · Python 3.12       │
│ · 模型适配器（可替换）            │
│ · 图像后处理（Pillow / OpenCV）  │
│ · 保真检查                       │
│ · Excel 导出 / 导入（openpyxl）  │
└──────────────────────────────┘
```

### 关键决定

- **Expo（React Native）**：一套代码覆盖安卓和 iOS，用原生相机和原生控件。抠图通过 Expo 原生模块调用系统能力，免费且在本机完成。iOS 包用 EAS 云端构建，不需要 Mac；小更新用 EAS Update 热更新。
- **Supabase**：账号、数据库、存储、队列、密钥都是现成的，**用行级权限在数据库层面保证"只有本人能看自己的数据"**。
- **Python 工作服务**：所有 AI 调用和图像处理都在这里完成，App 不直接调用模型。部署在一台常驻的小服务器上（Fly.io / Railway，第 1 期再定）。
- **所有 AI 任务都是异步的**：App 创建任务后可以继续操作，结果通过 Realtime 推回来。

## 4. 数据模型

所有表都带 `user_id`，RLS 规则统一为 `user_id = auth.uid()`。

| 表 | 主要字段 | 说明 |
|---|---|---|
| `profiles` | `id`(=auth uid), `nickname`, `height_cm`, `weight_kg`, `shoulder_cm`, `chest_cm`, `waist_cm`, `hip_cm`, `build`, `avatar_version`, `avatar_status` | 身材字段除身高、体重外都可为空 |
| `photos` | `id`, `user_id`, `kind`(garment / tag / mirror / body), `path`, `cutout_path`, `created_at` | 用户上传的所有原始照片 |
| `items` | `id`, `user_id`, `name`, `category`, `subcategory`, `colors` jsonb, `seasons` text[], `brand`, `size`, `material`, `price_cents`, `currency`, `purchased_on`, `purchase_channel`, `storage_location`, `fit_notes`, `status`(processing / review / active / archived), `catalog_path`, `source_photo_id`, `tag_photo_id`, `field_sources` jsonb, `embedding` vector | `field_sources` 记录每个字段的来源（ai / tag / user），用于 UI 标记。`embedding` 用于镜子照片识别单品（pgvector）|
| `item_candidates` | `id`, `item_id`, `path`, `fidelity` jsonb, `chosen` | 每次生成的候选商品图和保真检查结果 |

| `outfits` | `id`, `user_id`, `name`, `tags` text[], `created_at` | |
| `outfit_items` | `outfit_id`, `item_id`, `slot`, `layer_order`, `variant` | |
| `wear_logs` | `id`, `user_id`, `worn_on` date, `outfit_id`, `source`(manual / mirror), `mirror_photo_id` | |
| `wear_log_items` | `wear_log_id`, `item_id` | 穿着次数 = 计数 |
| `jobs` | `id`, `user_id`, `type`, `status`, `input` jsonb, `output` jsonb, `error`, `attempts`, `cost_usd`, `created_at`, `updated_at` | 任务记录，也是费用统计的来源 |

## 5. AI 流程

所有能力都放在统一接口后面，方便以后换模型：

```python
class CatalogGenerator(Protocol):   # 统一商品图
class Autofiller(Protocol):         # 识别属性 / 读吊牌
class AvatarGenerator(Protocol):    # 个人形象 8 角度
class LayerGenerator(Protocol):     # 上身图层
class ItemMatcher(Protocol):        # 镜子照片识别单品
class PhotoGenerator(Protocol):     # 真人大片
class VideoGenerator(Protocol):     # 360° 视频
```

**原则：所有 AI 能力尽量走同一个提供方**（比如一个聚合平台或同一家厂商），这样用户只需要注册一次、填一个 Key。具体选哪家由第 0 期技术实验决定。

### 5.1 统一商品图（第 1 期）

1. **本机预处理**：抠出衣服主体，裁剪。原图和抠图都上传。
2. **生成**：抠图 + 风格参考图 + 提示词，交给图像编辑模型，一次生成 2–3 个候选。提示词的约束是"**改拍摄，不改衣服**"：可以抚平褶皱、摆正角度、统一灯光、补全被遮挡的部分；不能改颜色、版型、纽扣和口袋的数量与位置、印花、logo、面料质感。
3. **标准化后处理**（确定性代码，不靠 AI）：再次抠图 → 按品类放到固定画布上（1200×1500，底色 `#F1F1F2`，按品类设定统一的留白和缩放）→ 加统一的柔和阴影。
4. **保真检查**：
   - 颜色：比较原图和生成图衣服区域的主色（CIEDE2000 色差），超过阈值就自动重新生成，最多重试 2 次。
   - 结构：用视觉语言模型对比两张图，逐项检查纽扣、口袋、印花、版型、衣长，输出清单显示在确认页上。
5. **用户确认**：挑一个候选，或者重新生成，或者"只存原图"（直接用标准化后的抠图）。

### 5.2 信息自动填（第 1 期）

视觉语言模型读取衣服照片（以及吊牌照片，如果有），按固定的 JSON Schema 输出字段和置信度。低置信度的字段留空，不乱填。`field_sources` 记录来源。

### 5.3 个人形象（第 2 期）

3 张全身照 + 身材数据 → 先生成正面形象（穿统一的中性打底衣），用户确认像不像 → 再以正面为参考生成其余 7 个角度。形象有版本号，更新形象后所有上身图层都要重新生成（提示用户费用）。

### 5.4 上身图层（第 2 期只做正面，第 3 期做 8 个角度）

商品图 + 某个角度的形象 → 生成"穿上这件衣服"的图 → 减去形象、只保留衣服区域 → 得到对齐到形象画布的透明 PNG 图层。叠穿顺序：鞋 → 下装 → 上衣 → 外套 → 包。上衣提供"塞进 / 不塞进"两个变体，外套提供"敞开 / 合上"两个变体（按需生成）。8 个角度**按需生成**：用户第一次转动查看某套穿搭时才生成，避免录入时一次性花太多钱。

### 5.5 镜子照片校准（第 2 期）

镜子照片 → 检测衣服区域 → 和衣橱单品的 embedding 做相似度匹配 → 用户确认 → 记一次穿着 → 以真实照片为参考，重新生成匹配单品的上身图层（标记 `calibrated`）→ 写合身笔记。

### 5.6 真人大片与 360° 视频（第 3 期）

把当前穿搭的图层合成在形象上 → 写实化生成，可以选场景 → 视频用图生视频模型生成原地转身。每次生成前显示预计费用。

### 5.7 费用估算（粗略，以第 0 期实测为准）

| 环节 | 每次大约 |
|---|---|
| 统一商品图（含候选和重试） | $0.05–0.15 |
| 信息自动填 | < $0.01 |
| 上身图层，正面 1 张 | $0.04–0.12 |
| 上身图层，8 角度 | $0.3–1.0 |
| 个人形象（一次性） | $1–3 |
| 真人大片 1 张 | $0.05–0.2 |
| 360° 视频 1 段 | $0.5–2 |

## 6. 隐私与安全

- 所有表开启 RLS，所有存储桶都是私有的，路径按 `{user_id}/...` 划分，App 只能拿到短时有效的签名 URL。
- 全身照、身材数据、镜子照片视为敏感数据：UI 上不显示具体数字，只显示"已填写"。
- 用户 API Key 只存在 Supabase Vault 里，App 永远拿不到明文，界面只显示后 4 位。
- 只选用承诺**不使用 API 数据训练模型**的 AI 提供方。
- "永久删除我的全部数据"：删除数据库记录（级联删除）、清空存储目录、删除 Vault 密钥、注销账号。

## 7. 错误处理

| 情况 | 处理方式 |
|---|---|
| 网络断开时拍照 | 本机排队，联网后自动上传 |
| 生成失败 | 自动重试，最多 3 次，间隔递增；最终失败时单品停在"待生成"，原图和抠图照样能用，用户可以手动重试 |
| 保真检查不通过 | 自动重新生成；仍不通过就在确认页标黄提示，由用户决定 |
| 没有 Key、Key 无效、余额不足 | 不创建 AI 任务，引导用户去"我的"页面处理；不影响衣橱的其他功能 |
| 超过月度花费上限 | 暂停新任务，提示用户提高上限 |
| 任务重复提交 | 任务带幂等键，同一张照片不会重复扣费 |

## 8. 测试策略

- **工作服务（Python）**：pytest 覆盖后处理（缩放、留白、底色、阴影的输出是确定的）、色差计算、任务状态流转、费用累计。模型适配器用假实现替换。另外维护一组"黄金样本"（第 0 期收集的真实照片）做回归对比。
- **数据库**：用 SQL 测试验证 RLS，确认用户 A 读不到、写不了用户 B 的任何数据。
- **App**：Jest + React Native Testing Library 测试组件和状态逻辑（换装叠层顺序、筛选、统计计算）；Maestro 在安卓模拟器上跑端到端流程（录入 → 确认 → 衣橱 → 试衣）。
- **iOS 真机**：每个版本通过 TestFlight 发给朋友，按检查清单反馈。开发环境里没有 iOS 模拟器。

## 10. 风险与未决问题

| 风险 / 问题 | 应对 |
|---|---|
| 生成模型改动衣服细节（保真） | 候选 + 保真检查 + 用户确认 + "只存原图"兜底；第 0 期重点测试 |
| 8 个角度之间不一致、图层对不齐 | 第 0 期验证；做不到就退回"只有正面 + 背面" |
| 镜子照片识别不准 | 识别结果始终由用户确认，不自动写入 |
| 朋友不会申请 API Key | 写一页图文引导；如果门槛太高，以后再考虑 App 内付费 |
| 具体用哪家 AI 提供方 | 第 0 期决定 |
| 工作服务部署在哪里（Fly.io / Railway） | 第 1 期计划中决定，二者都满足需求 |
